## 一句话结论

SaveLink 已公开发布 Windows 桌面版 v0.1.0、v0.2.0、v0.3.0 和 v0.4.0。发布后动态发现阶段 1 至 5 已完成：普通 EXE 与 Steam 游戏可先登记本机启动方式，由 SaveLink 启动并监测，在用户退出后推荐候选目录；用户确认后接管现有自动备份。`Hole Is Mine`、RUNE 版《暗黑地牢》和 `HowManyDudes` 已完成真实绿色版验收。

MVP 已完成正式回归验收，`TC-17` 移除游戏不删除真实存档和 `TC-41` 启动自检清理残留均已补测通过。恢复链路已增加小文件/中文路径回归测试，并把恢复后校验加强为 `content_hash + file_count + total_size`。

云同步已完成真实百度双设备完整闭环：设备 A 上传 zip + `.ok`，设备 B 只读发现、下载、双重校验、接收至独立仓库，再绑定本机假存档目录并由用户手动恢复。恢复文件与本机目标快照 SHA-256 一致。接收不会带入设备 A 路径，绑定不会自动恢复。后台维护和用户云操作现在具有独立占用类型，上传开始提示只在后端受理后出现；自动排队尚未实现。core 当前 147 项通过（J/L/Q5 三项真实环境测试默认忽略）；Tauri 40 个测试全绿。

2026-08-18，使用真实学习版 `Arcane.Trigger.Build.21206983` 验收程序识别。首次发现目录名称会被错误按前缀命中 Manifest 中的 `Arcane / 534870`；修复后桌面快捷方式、`GunWizard.exe` 和安装目录三种入口均显示 0 个匹配且禁止添加。测试未启动游戏，既有手动添加记录和真实存档未修改。

2026-08-28，真实学习版 `HowManyDudes.exe` 暴露错误 AppID 会误命中 Manifest 中 `DrainSim` 的问题。当前实现要求 AppID 对应的 Manifest 游戏名与 EXE、快捷方式或目录身份至少有一项归一化后完整相等，否则忽略该 AppID 及规则并按真实程序身份进入动态发现。真实游玩后，主存档 `C:\Users\daiqiang\AppData\Local\HowManyDudes\<用户编号>\Game` 成为高可信候选；浏览器资料目录被强制降为低可信且禁止确认，`.bak` 配对只作辅助信号。

2026-07-23，代强和朋友进一步使用两台真实电脑及非开发者普通百度账号完成全链路人工验收。结论：普通用户可以直接授权并使用 SaveLink，不需要注册百度开发者或创建自己的应用；SaveLink 通过百度开放 API 工作，不要求本机预先打开或持续运行百度网盘客户端。

2026-08-05，`v0.1.0` 已在 GitHub 发布绿色版 ZIP 与 SHA-256，Apache License 2.0 已落库；GitHub 为主仓库，Gitee 为国内镜像，代码和标签均已同步。当前发布 ZIP 生成时间早于标签中的最后一个应用代码提交，需重新打包并替换附件，确保二进制与 `v0.1.0` 标签完全一致。

## 当前架构状态

- 客户端形态：Windows 桌面 C/S 架构应用，Tauri 壳 + React 前端 + Rust 后端命令层。
- 核心逻辑：`savelink-core`，纯 Rust service/repo/store 抽象，独立于 Tauri。
- 数据持久化：SQLite，数据库位于用户 AppData 下。
- 快照仓库：当前由 `FsStore` 以目录形式管理，实际数据位于用户 AppData 下的 `repository/`。
- 前后端调用：React 组件通过 `src/lib/api.ts` 统一调用 Tauri `invoke`，组件内不直接散落 invoke。
- 云同步路线：不再以 `latest.zip` 或整库 `savelink.db` 原样同步作为主线；百度网盘 POC 已通过，云端快照协议 v1 已定稿为按游戏目录发现的单快照 zip + `.ok`；详见 `SaveLink云端快照协议V1.md`。
- 云存储适配：`SqliteRepo` 已实现 `CloudStateRepository`；`FakeCloudObjectStore` 保护无网络同步测试；`BaiduNetdiskStore` 将逻辑路径映射到 `/apps/savelink/v1/`，实现真实 HTTP 对象操作。
- 百度账号连接：Tauri 已提供连接状态和发起授权命令；Token 独立保存在 AppData `credentials/baidu-oauth.json`，SQLite `cloud_accounts` 只保存 `token_ref`。
- 自动备份：Tauri 后台线程启动立即检查，之后每 10 分钟检查；全局开关持久化在 `app_settings`，默认开启。
- 自动上云：仅自动创建的快照由后台立即上传；未授权不弹浏览器，授权失效、断网和限流时保留本地等待后续周期重试。
- 自动保留：所有来源的未锁定记录统一计入可配置上限，默认 10、范围 1 到 100；锁定记录不计入；云端 `.ok`、`.zip` 删除成功后才删除本地快照。
- 快照详情一致性：每次打开详情时异步扫描当前真实存档，以同一算法比较内容哈希、文件数量和总大小，显示一致、不一致或无法检查；该操作不创建快照、不写真实存档、不更新 SQLite，也不等待云同步写锁，前端 15 秒超时兜底。
- 时间口径：快照时间在 SQLite 中统一为秒精度 UTC RFC 3339；旧本机分钟格式和带偏移云端格式自动迁移，界面统一按用户本地时区显示。
- 模拟器来源：DeSmuME 使用 `SaveSource::Files` 只保护共享 `Battery` 中当前 ROM 对应的 `.dsv`；快照内逻辑文件名稳定为 `save.dsv`，跨设备恢复时再映射到目标设备的 ROM 文件名。
- ROM 身份：保存 SHA-256、NDS Header Title 和 Game Code，不上传 ROM；设备本机路径只在 `emulator_binding` 中持久化，不进入云协议。
- 普通游戏启动绑定：仅在本机 `games.launch_binding` 保存 EXE、安装目录、受控启动参数和可选 Steam AppID，不进入百度云端 `game.json`。
- 配置状态：有存档来源为已配置；无存档来源但有启动绑定为待发现；两者都没有为待绑定。待配置游戏不能创建、恢复或上传快照，自动备份正常跳过。
- 已配置且有普通 EXE/Steam 启动绑定的游戏可通过“启动游戏”直接启动；该动作不创建动态发现监听、不记录 PID、不展示候选。已配置游戏的自动备份仍由启动检查和 10 分钟轮询负责。

## 已完成功能

### 1. 游戏管理

- 从真实 Steam 安装和随包 Ludusavi Manifest 数据库自动发现可识别游戏，同时保留手动添加。
- “游戏程序”当前只允许选择 Windows 快捷方式或游戏 EXE；后端仍保留有限安装目录扫描能力，供内部回归和未来入口复用。
- AppID 对应的 Manifest 游戏名必须与快捷方式、EXE 或目录身份至少有一项完整相等；名称冲突时忽略 AppID。无可靠 AppID 时只接受完整名称相等，并只展示实际存在的存档候选。
- 从 DeSmuME 目录和 `desmume.ini` 发现 ROM，读取 NDS Header 身份并精确匹配对应 `.dsv`；配置 ROM 目录失效时要求用户重新选择。
- 添加游戏时可一次绑定一个或多个存档目录；纯配置路径单独展示且默认不保护。
- 普通 EXE/手动添加必须选择真实游戏 EXE；Steam 自动发现保存 `steam.exe + -applaunch AppID`；DeSmuME 继续使用模拟器/ROM 绑定。
- 已有旧游戏再次从 Steam 或“游戏程序”添加时，会为原记录补充启动绑定，不创建重复游戏；EXE、由 EXE 推导的安装目录、Steam AppID 和存档目录均参与跨入口防重。
- 未识别到存档目录的普通 EXE 游戏可先登记为“待设置存档目录”，此时明确显示当前不会创建备份。
- 测试读取目录，显示文件数量和总大小。
- 游戏列表展示游戏名、快照数量、最近快照时间。
- 游戏信息落库，关闭再打开仍保留。
- 编辑游戏名称。
- 编辑游戏存档路径。
- 编辑时可重新选择目录、测试读取、保存修改。
- 移除游戏。
- 移除游戏会删除 SaveLink 内部的该游戏记录、快照记录和快照仓库文件。
- 移除游戏不会删除真实存档目录。

### 2. 快照创建与管理

- 手动创建快照。
- 如果存档未变化，创建快照返回“无变化”，不重复写入新快照。
- 快照时间线展示创建时间、备注、文件数量、大小、创建原因。
- 快照备注可编辑；目前备注基本承担了“快照命名”的作用。
- 快照可锁定/取消锁定。
- 锁定快照不能删除。
- 未锁定快照可删除。
- 旧版 `before_restore` 记录继续作为普通历史备份展示，当前版本不再创建。

### 3. 恢复流程

- 可从时间线恢复指定快照。
- 恢复前先校验目标快照，目标损坏则不碰真实存档。
- 当前已等于目标时不执行覆盖；其余情况直接恢复，不自动创建或复用快照。
- 确认页提醒第一版不会自动备份当前存档，用户若需保留当前进度应先手动创建快照。
- 恢复采用同盘临时目录 + rename 替换，`.old` 在最终校验通过后才删除；校验失败会尝试恢复原目录。
- 恢复后会校验真实存档内容与目标快照一致。
- 恢复失败文案已按错误类型优化：
  - 快照损坏、备份失败、已回滚的恢复失败：明确提示本次恢复未修改真实存档。
  - 未回滚的极端恢复失败：保留谨慎提示，要求用户核对存档目录。
- 存档目录缺失时，已支持“创建目录并恢复”。
- 存档目录缺失时，用户也可以取消。
- “重新选择目录并恢复”暂未做，因为它和更完整的“编辑游戏路径/恢复联动”有关，目前不是核心缺口。

### 4. 版本信息与设置入口

- 当前版本号直接显示在首页 SaveLink 标题旁。
- 顶部齿轮打开设置页，当前展示全局“自动备份”开关和“快照保留数量”；保留数量默认 10，可设置为 1 到 100。已有游戏的旧数据库会在用户确认前保留原有超出快照。

- opener scope 继续只允许 `$APPDATA` 和 `$APPDATA/**`，不开放整个磁盘。

## 已知未完成或需要总规划判断的点

当前本地快照仓库能用，但不是压缩包。后续如果关心空间占用和快照文件数量，可以规划 ZipStore 或 ResticStore。这不阻塞云同步：上传时将 `repository/snapshots/{snapshot_id}/` 临时打包为单快照 zip；下载后完成双重校验，再通过 `FsStore` 写入本机 `repository`。

### 2. Steam 父子候选问题已修复，剩余实机复验

多存档目录已贯通扫描、快照、恢复、存储、云协议和前端。Elden Ring 的 `<storeUserId>` 通配符误匹配同级 `GraphicsConfig.xml` 已修复：末尾用户目录占位符只接受目录，Manifest 结果会收敛父子路径，所有添加、编辑、创建和恢复入口也拒绝重叠目录。自动测试、真实开发版和绿色版候选均已通过；仅真实多 Steam 游戏库仍待以后验收。

## v0.2.0 完成状态

v0.2.0 的目标是让 SaveLink 定期检测存档变化，自动创建快照并立即上传百度网盘。当前权威方案见 `SaveLink-v0.2.0自动备份方案.md`。

已确认：

1. 启动后立即检查一次，之后默认每 10 分钟检查一次。
2. 自动备份使用全局开关并默认开启，作为设置页第一个正式设置项。
3. 内容变化才创建快照，游戏运行期间允许读取，但不得发布不稳定或未校验的文件。
4. 本地快照成功后立即上传百度网盘。
5. 每个游戏默认保留最近 10 个未锁定历史记录；设置页可调整为 1 到 100 个。锁定记录不计入上限、不设数量上限且不会被自动清理。
6. 删除旧记录的最终目标同时覆盖本地仓库和百度网盘，不能只实现本地清理。
7. 多设备冲突由用户选择，不允许后台自动覆盖。

本地专项、真实百度上传、跨 profile 下载恢复、历史联合删除、旧库时间迁移和设备 B 本地化显示均已验收。手动、自动和云端接收的完整未锁定快照已经统一计入可配置上限。默认 10、范围 1 到 100 的设置功能已接入，待本轮实机验收。

发布后继续补充但不阻塞本次发布的项目：真实断网重试、Token 失效或限流、真实百度删除中途失败、另一设备提前删除对象，以及多设备冲突选择交互。npm、Cargo、Tauri 和打包元数据已统一为 `0.4.0`，正式绿色版 ZIP 和 SHA-256 待生成。
