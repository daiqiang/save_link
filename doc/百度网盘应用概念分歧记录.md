# 百度网盘开放平台“应用”概念分歧记录

## 版本历史

| 版本 | 修改人 | 时间 | 备注 |
| --- | --- | --- | --- |
| 1.0 | 代强 | 2026-05-21 | 第一版：记录关于百度网盘开放平台“应用”是否存在两层创建流程的分歧，并根据开发者注册与创建应用结果更新判断 |

## 背景

在准备进行百度网盘 API 技术可行性调研时，我们对百度网盘开放平台文档里的“创建应用”概念产生了分歧。

这个问题很重要，因为它直接影响 SaveLink 的产品可用性：

- 如果普通用户也需要在百度开放平台创建自己的应用，产品门槛会非常高，基本不可接受。
- 如果只需要 SaveLink 开发者创建一个官方应用，普通用户只做 OAuth 授权，那么百度网盘 API 路线仍然有产品化可能。

## 用户当前理解

用户的理解是：可能存在两个不同的应用。

```text
第一层：
开发者注册百度开放平台账号后，创建一个名为 SaveLink 的应用。

第二层：
当开发者或用户真正要使用百度网盘 API 时，还需要在百度网盘相关平台里再创建一个类似 my_test_storage 的应用。
```

用户担心的是：

- 开发者创建 SaveLink 应用可能只解决“开发者身份”问题。
- 后续每个用户实际使用百度网盘 API 时，可能还要自己创建一个属于自己的 `my_test_storage` 应用。
- 如果真是这样，普通用户会被迫进入百度开放平台、实名认证、创建应用，使用门槛不可接受。

用户希望验证：

> 能否由 SaveLink 开发者统一创建应用，避免每个用户自己创建 `my_test_storage` 这类应用。

## Codex 当前判断

Codex 当前判断是：不存在必须创建两层不同应用的流程。

更可能的模型是：

```text
百度开发者账号
  └─ 开放平台应用：SaveLink / SaveLinkTest / my_test_storage
       └─ 用户授权后，在用户网盘里产生对应的应用数据目录
```

也就是说：

- `SaveLink`、`SaveLinkTest`、`my_test_storage` 更像是同一层级的开放平台应用名称。
- 开发者可以创建一个测试应用叫 `my_test_storage`，也可以创建一个测试应用叫 `SaveLinkTest`。
- 未来正式产品只需要一个 SaveLink 官方应用。
- 普通用户不应该创建应用，只需要授权 SaveLink 应用访问自己的百度网盘。

用户侧预期流程应该是：

```text
用户打开 SaveLink
→ 点击“连接百度网盘”
→ 百度授权页显示：SaveLink 请求访问你的网盘
→ 用户登录/扫码并同意授权
→ SaveLink 获得该用户的 access_token / refresh_token
→ SaveLink 在该用户网盘的应用目录中读写快照数据
```

可能出现的 `/apps/SaveLink/` 或类似目录，不是用户创建的“应用”，而是百度根据开放平台应用自动隔离出来的应用数据目录。

## 分歧核心

双方分歧不在于“是否需要创建应用”。

双方都认可：

- 开发者需要注册百度开放平台。
- 开发者需要实名认证。
- 开发者需要创建应用。
- 应用需要 AppKey / SecretKey / OAuth 授权配置。

真正分歧在于：

> 普通用户是否也需要创建自己的百度开放平台应用？

用户担心答案是“需要”。  
Codex 当前判断答案是“不需要，只需要授权 SaveLink 官方应用”。

## 待实验验证问题

接下来实验时，需要重点验证以下问题：

1. 创建一个开发者应用后，能否用同一个应用给当前百度账号授权并调用网盘 API。
2. 换另一个普通百度账号时，是否只需要授权同一个应用，而不需要登录开放平台创建新应用。
3. OAuth 授权页展示的是不是开发者创建的应用名称，例如 `SaveLinkTest`。
4. 授权成功后，云端目录是否自动出现在 `/apps/应用名/` 或类似应用数据空间。
5. 是否存在另一个必须由用户手动创建的 `my_test_storage` 类型应用。
6. 如果文档里的 `my_test_storage` 只是示例应用名，是否可以完全替换成 `SaveLinkTest`。
7. 如果用户不创建应用，只授权 SaveLinkTest，上传、下载、列目录、删除是否能正常工作。

## 建议实验路径

第一步：开发者侧创建测试应用。

```text
应用名：SaveLinkTest
用途：百度网盘 API 上传下载 POC
```

第二步：用开发者自己的百度账号授权 `SaveLinkTest`。

目标：

- 获取 access_token / refresh_token。
- 上传一个测试文件到应用目录。
- 列出应用目录文件。
- 下载该测试文件。

第三步：换一个普通百度账号授权同一个 `SaveLinkTest`。

目标：

- 不登录开放平台。
- 不创建应用。
- 只通过 OAuth 授权。
- 验证是否也能上传、下载、列目录。

如果第三步成功，则说明：

> 普通用户无需创建自己的应用，只需要授权 SaveLink 官方应用。

如果第三步失败，则需要记录失败原因：

- 是否因为应用处于测试状态，只允许开发者账号或测试账号授权？
- 是否需要配置测试用户白名单？
- 是否需要正式上线审核后才允许任意用户授权？
- 是否确实要求用户自己创建应用？

## 后续验证结果

用户已经在百度开放平台注册成为开发者并创建了应用。

基于实际注册和创建应用流程，当前更倾向确认：

- 百度开放平台的“创建应用”是开发者侧动作。
- 未来 SaveLink 用户不需要创建自己的开放平台应用。
- 用户侧流程应为：打开 SaveLink，点击连接百度网盘，进入百度授权页，同意授权后，SaveLink 获得该用户的 access_token，并在该用户网盘的应用目录中读写文件。
- “应用目录”是授权后用于隔离应用数据的目录，不是用户另行创建的开放平台应用。

因此，原分歧中的核心风险已经明显降低。

仍可在正式开发前补充验证：

- 未注册开放平台的普通百度账号是否可以直接授权 SaveLink 测试应用。
- 测试阶段是否存在授权用户白名单或数量限制。
- 正式上线审核后，任意普通用户是否都可以授权 SaveLink 应用。

## 当前结论

目前可以认为：用户无需创建自己的百度开放平台应用。

基于 OAuth 和开放平台的一般设计，以及用户完成开发者注册和创建应用后的观察：

- 创建应用是 SaveLink 开发者的工作。
- 普通用户只需要授权同一个 SaveLink 应用。
- `/apps/应用名/` 是应用数据目录，不是用户另行创建的应用。

如果后续正式 API POC 出现相反证据，再更新本文档。
