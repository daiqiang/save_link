## 背景与问题

SaveLink 当前可以从 Steam、游戏程序、DeSmuME 或手动目录添加游戏。游戏程序识别依赖安装目录中的 AppID 配置和 Ludusavi Manifest；当规则库没有收录新游戏，或学习版携带了不可信的模拟 Steam AppID 时，会出现以下情况：

- 已选中正确 EXE，但找不到存档目录。
- 不同学习版游戏可能携带相同的 `steam_appid.txt`，从而被错误识别为同一个 Manifest 游戏。
- 存档实际写入 `LocalLow`、`Roaming` 或其他用户目录，路径与 AppID 没有必然关系。
- 用户甚至无法手动找到存档目录，现有“手动添加”也无法完成。

已知真实样本 `Hole Is Mine` 的正式 Steam AppID 是 `4508020`，学习版兼容层却包含 `2963800`；主要进度实际写入：

```text
C:\Users\<用户>\AppData\LocalLow\Incrementalist\Hole Is Mine\Save\Steam\<用户编号>\Release
```

另一个真实样本 `HowManyDudes.exe` 携带的 AppID 会错误指向 Manifest 中的 `DrainSim`，不能把学习版随附 AppID 当作充分身份依据。当前规则要求 AppID 对应的 Manifest 游戏名与快捷方式、EXE 或目录身份至少有一项归一化后完整相等；名称冲突时忽略 AppID 和对应存档规则，按真实程序身份进入动态发现。该游戏的主存档实际位于：

```text
C:\Users\daiqiang\AppData\Local\HowManyDudes\<用户编号>\Game
```

游戏自带的 `C:\Users\daiqiang\AppData\Local\HowManyDudes\Backup\<用户编号>\Game` 也会随游玩变化，当前可能与主存档并列高可信；这属于候选排序/提示待优化项，用户应只确认不含 `Backup` 的主存档。

而 `Roaming\GSE Saves\2963800\playtime.txt` 只是模拟层数据，不能替代主要游戏进度。

因此新功能不能继续把 AppID 当作唯一事实。它需要观察一次真实游戏会话中的文件变化，给出候选目录，再由用户确认。

## 核心产品决定

### 1. 添加游戏与完成保护是两个阶段

用户选择 EXE 并确认后，游戏立即进入 SaveLink，即使此时还没有存档目录。

此时必须明确显示：

```text
待设置存档目录
当前不会创建备份
```

只有用户确认至少一个存档目录后，游戏才进入可创建快照和自动备份的状态。

### 2. SaveLink 负责启动游戏和控制监测窗口

主流程不是让用户自行计算何时开始、何时停止监测，而是：

```text
SaveLink 先启动监测
-> SaveLink 启动已登记的游戏 EXE
-> 记录启动进程 PID
-> 用户正常游玩并退出
-> SaveLink 检测进程结束并等待短暂宽限期
-> 自动停止监测和分析
```

“手动停止并分析”始终保留，处理启动器、进程转交或游戏异常退出等兼容情况。

### 3. 同时只允许一个动态发现会话

目录监测覆盖多个公共用户目录。多个游戏同时监测会让事件归属无法解释，因此第一版全局只允许一个活动会话。

### 4. 候选目录必须由用户确认

`ReadDirectoryChangesW` 能证明“某个路径在游戏运行时间窗口内发生变化”，不能证明“该文件一定由目标 PID 写入”。因此 SaveLink 只做排序和推荐，不自动绑定目录。

### 5. 动态发现不自动修改真实文件

监测、分析和候选展示必须保持只读。用户确认目录前，不创建快照、不上传、不恢复，也不修改游戏文件或存档。

### 6. 普通 PC 游戏必须登记本机启动方式

普通 EXE 游戏和 Steam 游戏都必须有本机启动绑定，不能再创建“只有存档目录、没有启动方式”的新记录：

- 普通游戏保存真实 EXE 和安装目录。
- Steam 游戏保存 `steam.exe`、受控参数 `-applaunch AppID`、AppID 和游戏安装目录。
- DeSmuME 继续使用模拟器根目录与 ROM 的现有本机绑定，不重复写普通启动绑定。
- 从“游戏程序”或 Steam 再次添加已有旧游戏时，应给原记录补充启动绑定，不创建同一游戏的第二条记录。

旧测试数据如果没有真实可执行程序，不伪造路径；它可以保留为“待绑定”数据，但不能作为新建行为的范例。

## 完整用户流程

### 阶段 A：登记游戏

1. 用户点击“添加游戏”，进入“游戏程序”。
2. 用户选择直接游戏 EXE；Windows 快捷方式可解析为直接目标 EXE。
3. SaveLink 执行现有只读程序识别，展示游戏名称、EXE、安装目录和可能的 Manifest 匹配。
4. 来自学习版配置的 AppID 只作为参考，不再表述为绝对可信的“精确身份”。
5. 如果已有可信且真实存在的存档目录，用户仍可沿用现有流程直接添加为已配置游戏。
6. 如果没有存档目录，或用户不信任当前匹配，用户点击“添加到 SaveLink”。
7. SaveLink 保存游戏名称、EXE 和安装目录，允许 `save_paths` 为空。
8. 游戏立即出现在首页，显示“待设置存档目录”和“当前不会创建备份”。

选择文件不等于添加成功。仍需保留一次明确的“添加到 SaveLink”确认，避免误选 EXE 后留下无意创建的游戏记录。

### 阶段 A+：已配置游戏直接启动

1. 用户在已经设置存档目录、且存在本机 EXE/Steam 启动绑定的普通游戏上点击“启动游戏”。
2. SaveLink 校验启动程序和安装目录仍然存在。
3. SaveLink 直接启动已保存的 EXE，或按受控参数启动 Steam 的 `-applaunch AppID`。
4. 本流程不建立 `ReadDirectoryChangesW` 监听器，不记录 PID，不进入动态发现候选分析，也不改变发现状态。
5. 游戏运行期间，已配置游戏仍由原有自动备份机制在启动时和每 10 分钟轮询；用户也可以继续手动创建快照。

没有启动绑定、正在进行另一款游戏的动态发现，或游戏启动文件已被移动时，直接启动应失败并显示明确错误，不降级为动态发现。

### 阶段 B：启动游戏并发现存档

1. 用户在待配置游戏上点击“启动游戏并查找存档”。
2. SaveLink 检查当前没有其他动态发现会话。
3. SaveLink 解析并校验监听根目录，排除不存在或不能访问的位置。
4. SaveLink 启动所有目录监听器，并确认监听器已经进入工作状态。
5. 只有监听器全部准备完成后，SaveLink 才启动游戏 EXE。
6. SaveLink 保存启动 PID、开始时间和游戏 ID。
7. 用户正常游玩，并至少触发一次真实进度保存。
8. SaveLink 在后台记录监测范围内的创建、修改、重命名和删除事件。
9. 用户可以关闭主窗口到托盘；监测继续。
10. SaveLink 检测主游戏进程结束。
11. SaveLink 继续监听一个短暂宽限期，第一版建议 5 秒，覆盖退出阶段异步落盘。
12. SaveLink 停止监听，合并事件并生成候选目录。
13. SaveLink 主窗口展示分析结果；如果窗口隐藏，可显示托盘通知并在游戏卡片显示“等待确认”。

### 阶段 C：确认目录并开始保护

1. 页面按高、中、低可信度展示候选目录。
2. 每个候选显示本次变化的文件、事件类型、最后变化时间和降权原因。
3. 用户选择一个或多个候选目录。
4. SaveLink 校验目录存在、可读取、没有重复、没有父子嵌套，也没有被当前游戏重复选择。
5. 用户确认后，SaveLink 将目录写入该游戏的本机配置。
6. 游戏从“待设置存档目录”切换为“已配置”。
7. 全局自动备份开启时，立即为该游戏执行一次自动检查：
   - 有内容且能稳定读取：创建第一份 `reason=auto` 快照，并沿用现有自动上传规则。
   - 内容与已有快照相同：不重复创建。
   - 创建失败：保留已经确认的目录，明确显示首次备份失败并允许重试。
8. 全局自动备份关闭时，不偷偷创建自动快照；页面显示“存档目录已设置，自动备份已关闭”，并保留手动创建快照入口。
9. 后续交给现有启动检查和每 10 分钟自动备份体系。

## 状态模型

### 持久状态

持久状态由本机游戏数据推导，避免额外状态字段与真实数据漂移：

| 条件 | 状态 | 用户含义 |
| --- | --- | --- |
| 有有效 `save_sources` 或 `save_paths` | 已配置 | 可以创建快照和恢复；有普通 EXE/Steam 启动绑定时还可以直接启动游戏；是否自动运行还取决于全局自动备份开关 |
| 没有存档来源，存在本机 EXE 绑定 | 待发现存档 | 已添加游戏，但当前不会备份；阶段 3 接入启动游戏并查找存档 |
| 没有存档来源，不存在 EXE 绑定 | 待绑定本机目录 | 主要用于云端下载到设备 B 的游戏，继续使用现有绑定目录流程 |

DeSmuME 继续使用现有 ROM 绑定语义，不进入普通 EXE 动态发现流程。

### 临时会话状态

动态发现会话只存在于当前 SaveLink 进程内，第一版不写 SQLite：

```text
idle
-> starting_watchers
-> launching_game
-> monitoring
-> exit_grace_period
-> analyzing
-> awaiting_confirmation
-> completed
```

任意阶段可进入：

```text
failed
cancelled
```

应用真正退出后临时结果可以丢弃，游戏仍保持“待发现存档”，下次可重新监测。关闭窗口到托盘不算退出，会话继续。

### 首页标识

待发现游戏至少需要三层提示：

- 游戏列表：醒目的“待配置”状态，不与快照数量混淆。
- 游戏详情：显示“尚未设置存档目录，当前不会创建备份”。
- 待发现游戏主操作：“启动游戏并查找存档”；已配置且有启动绑定的普通游戏主操作为“启动游戏”。

未配置时必须禁用或隐藏：

- 创建快照。
- 恢复快照。
- 上传快照。

自动备份遇到空来源游戏应正常跳过，不记为失败。

## 本机数据模型

普通游戏需要增加可选的本机启动绑定。推荐模型：

```rust
pub struct GameLaunchBinding {
    pub executable_path: PathBuf,
    pub install_dir: PathBuf,
    pub launch_arguments: Vec<String>,
    pub steam_app_id: Option<u32>,
}
```

普通 EXE 的 `launch_arguments` 为空、`steam_app_id` 为 `None`。Steam 绑定只允许 SaveLink 自己构造 `-applaunch <AppID>`，不接受用户输入任意命令行；`steam_app_id` 同时作为跨 Steam 安装位置稳定识别同一启动目标的本机身份。工作目录仍从绑定的安装目录推导。第三方启动器任意参数和管理员启动暂不支持。

`Game` 增加：

```rust
pub launch_binding: Option<GameLaunchBinding>
```

SQLite `games` 表增加一个可空 JSON 字段或两个可空路径字段。实现前的技术设计优先比较：

- 单个 JSON 字段：便于未来增加工作目录、参数种类和启动方式。
- 两个路径字段：查询直观，但后续扩展需要继续迁移。

当前已使用可空 JSON 字段，并有旧数据库无损迁移测试。新添加的普通 PC 游戏必须写入该字段；云端接收或确实无法推断的旧数据可以暂时为 `None`，等待用户在本机补绑。

## 云端与隐私边界

以下信息只属于当前设备：

- 游戏 EXE 绝对路径。
- 安装目录。
- 动态发现会话及原始文件变化事件。
- 候选存档绝对路径。

它们不得进入：

- 百度网盘 `game.json`。
- 云端 `.ok`。
- 其他设备接收的游戏身份。
- 前端日志或普通错误日志中的完整事件流水。

云端下载到设备 B 的游戏仍不继承设备 A 的 EXE 或存档路径。设备 B 可以继续手动绑定目录；以后如需通过 EXE 重新发现，应由设备 B 单独选择本机 EXE。

## 监听范围

第一版不监听整个 C 盘、D 盘，也不遍历所有文件。建议递归监听以下根目录中实际存在且可访问的部分：

1. 游戏安装目录。
2. `%LOCALAPPDATA%`。
3. `%USERPROFILE%\AppData\LocalLow`。
4. `%APPDATA%`。
5. 当前用户 Documents。
6. 当前用户 Saved Games。
7. 公共文档下实际存在的已知 Steam 模拟器数据根目录，第一批为 `Steam\RUNE` 和 `Steam\CODEX`。

Documents 和 Saved Games 应优先通过 Windows Known Folder API 获取，不依赖固定英文目录名。

公共文档同样通过 Windows Known Folder API 定位。只监听实际存在的模拟器根目录并递归覆盖其 AppID 子目录，不监听整个 Public Documents，也不依赖先找到或解析游戏目录中的模拟器配置。对 `RUNE`/`CODEX` 两个已知根，紧跟的纯数字目录是游戏 AppId 容器；子树内任何变化都归并为整个 `<AppId>` 候选。`%APPDATA%` 已经覆盖 Goldberg、FLT 等位于 Roaming 下的数据，不重复建立嵌套监听器。

必须排除 SaveLink 自己的数据目录和快照仓库，避免自动备份或云同步事件反过来污染发现结果。

监听事件类型：

- 文件或目录创建。
- 文件内容/大小/最后写入时间变化。
- 文件或目录重命名。
- 文件或目录删除。

不监听仅访问时间，避免普通读取制造大量噪声。

## `ReadDirectoryChangesW` 实现原则

Windows 后端采用窄范围原生 `ReadDirectoryChangesW` 适配层。技术验证确认 `notify 8.2.0` 的 Windows 后端确实使用该 API，常规事件和停止行为可用，但没有可靠地把 Windows 内核缓冲区溢出传递给业务层，因此不满足本功能的完整性要求。

监听器必须满足：

- 先确认监听成功，再启动游戏。
- 多根目录并行监听。
- 可以主动停止，不依赖文件再次变化才能退出线程。
- SaveLink 真正退出时关闭句柄和工作线程。
- 单个根目录失败时明确报告，不静默缩小监测范围后继续给出“完整”结果。
- 事件缓冲区溢出时将本次会话标记为不完整，要求用户重试，不能把残缺结果伪装成可靠候选。
- 设置事件数量、候选数量和内存上限，防止高频日志写入无限占用内存。

### 阶段 1 技术验证结论

2026-08-24 在独立 `save_link_poc/save-activity-poc` 中完成验证：

- `cargo test --no-fail-fast`：2 个测试通过。
- release 自检 11 项全部通过，并连续执行三轮保持全绿。
- `notify` 完成多目录、增删改名、中文路径、超过 260 个 UTF-16 单元的长路径、PID、宽限期和快速启动器实验。
- 原生 Win32 探针完成增删改名解析、两个目录句柄并行、超过 260 个 UTF-16 单元的中文长路径、`CancelIoEx` 停止和内核溢出识别。
- 64 字节原生缓冲区无法容纳长文件名时，能够通过 `bytes_written == 0` 或 `ERROR_NOTIFY_ENUM_DIR` 明确标记 overflow。

正式实现采用每个根目录一个异步句柄/工作线程、统一取消和有界事件收集器。所有监听器就绪后再启动游戏；任一监听失败或溢出时，本次会话整体标记为不完整。详细证据见 POC 的 `技术验证报告-20260824.md`。

## 游戏启动与 PID 生命周期

### 第一版正式支持

- 用户直接选择的游戏 EXE。
- 目标直接指向游戏 EXE 的 Windows 快捷方式。
- 使用 EXE 所在目录作为工作目录。
- SaveLink 启动后记录主 PID，主 PID 退出后进入 5 秒宽限期。

### 启动器兼容问题

部分游戏生命周期是：

```text
launcher.exe
-> game.exe
-> crash-handler.exe
```

如果主 PID 在很短时间内退出，不能立即断言游戏已经结束。第一版采用保守策略：

- 主 PID 在建议阈值 10 秒内退出时，页面提示“启动进程已退出，可能已转交给启动器”。
- 监测继续运行，不自动分析。
- 用户在真正退出游戏后点击“停止并分析”。

技术验证阶段可以评估 Job Object 或子进程枚举，但不能在验证前承诺自动覆盖所有启动器。Job Object、Steam URI、反作弊、管理员权限和脱离父进程树的启动器均属于兼容增强，不阻塞直接 EXE 第一版。

### 启动失败

如果游戏启动失败：

- 立即停止本次监听。
- 不保留空的候选结果。
- 游戏仍为“待发现存档”。
- 显示可操作的错误，例如文件不存在、权限不足或系统拒绝启动。

## 事件聚合与候选评分

### 原始事件模型

核心分析层使用平台无关事件：

```rust
pub struct FileActivityEvent {
    pub path: PathBuf,
    pub kind: FileActivityKind,
    pub observed_at: SystemTime,
}
```

同一文件的连续变化先合并，再按直接父目录聚合。分析层不读取文件内容，只读取必要的路径和元数据。

### 加分信号

- 游戏运行期间创建或修改多个不同文件。
- 同一组文件在保存操作后集中变化，然后保持安静。
- 退出前后仍有写入。
- 路径包含程序名称、游戏名称、开发商名称或常见存档层级。
- 文件不是明显日志/缓存，且修改后仍真实存在。
- 同一目录内出现主文件和备份文件，例如 `.hole` 与 `.hole.bac`。

### 降权信号

- 只变化 `Player.log`、崩溃日志或 `playtime.txt`。
- 位于 `cache`、`logs`、`analytics`、`shader`、`temp`、`crash` 等目录。
- 高频持续写入但没有稳定数据文件。
- 只有配置文件变化，没有任何类似进度数据的其他文件。
- 目录就是过大的安装根目录或公共 AppData 根目录。

不能使用“已知存档扩展名白名单”硬过滤。新游戏可能使用 `.hole`、无扩展名或自定义格式，未知扩展名必须保留参与分析。

### 展示而不是隐藏

低可信变化默认折叠，但用户可以展开查看。除 SaveLink 自身目录和明确系统噪声外，不应把未知事件永久丢弃，否则无法解释漏报。

### 候选目录安全

如果变化文件直接位于游戏安装根目录，不能默认推荐把整个安装目录作为存档目录，否则可能备份整个游戏。第一版应显示风险提示并禁止一键确认过大的根目录；精确文件保护或安装根目录中的存档文件集合留作后续增强。

## Tauri 会话管理

`AppState` 增加全局动态发现管理器，持有至多一个活动会话：

```text
Arc<Mutex<Option<ActiveSaveDiscoverySession>>>
```

建议命令边界：

```text
add_program_game
start_save_discovery
get_save_discovery_status
stop_save_discovery
confirm_save_discovery_paths
cancel_save_discovery
```

`confirm_save_discovery_paths` 使用专用命令，而不是前端自行拼接多个旧命令。该命令负责一次性完成：

1. 验证会话和游戏一致。
2. 验证所选路径确实来自本次候选或经过明确人工补选。
3. 调用现有存档来源重叠校验。
4. 更新本机游戏路径。
5. 在自动备份开启时触发该游戏的首次检查。

状态变化通过 Tauri 事件通知前端；前端重新打开页面时仍可调用状态查询恢复当前显示。

以下操作在活动会话期间需要协调：

- 再次开始监测：拒绝，并显示当前正在监测的游戏。
- 删除当前游戏：要求先停止会话。
- 修改当前游戏 EXE：要求先停止会话。
- 关闭窗口到托盘：继续监测。
- 从托盘真正退出：停止监听、清理句柄后退出。

## 模块建议

### `savelink-core`

- `save_activity.rs`：平台无关事件、聚合、过滤、评分和候选模型。
- `save_discovery.rs`：发现会话的核心状态和结果模型。
- Windows 监听适配器：尽量保持窄接口，原始 Win32 句柄不得泄漏给业务服务。
- 模型和 SQLite：增加本机 `launch_binding`，并补迁移测试。

### `savelink-app/src-tauri`

- `save_discovery_runtime.rs`：启动 EXE、PID 等待、宽限期、后台线程和 Tauri 事件。
- `commands.rs`：只做 DTO、输入校验和调用编排。
- `lib.rs` / `desktop.rs`：命令注册和真正退出时的清理。

### React

- `api.ts`：动态发现命令统一入口。
- `types.ts`：持久配置状态、会话状态和候选 DTO。
- `AddGameDialog`：允许没有存档目录时先添加 EXE 游戏。
- 游戏详情：待配置标识、启动监测、监测进度、候选确认和手动停止。

监测 UI 不应长期塞在“添加游戏”弹窗中，因为游戏已经先进入首页，而且窗口可能在整个游玩期间关闭到托盘。添加弹窗只负责登记；监测和确认应属于已登记游戏的详情流程。

- `playtime.txt` 单文件目录被降权但仍可展开。
- `.hole` 等未知扩展名不会被过滤。
- 浏览器用户资料目录强制为低可信且不可确认。
- `.bak` 配对只能辅助加分，不能单独构成游戏存档证据。
- 候选目录排序稳定。
- SaveLink 自身数据目录被排除。
- 相同及父子候选不能同时确认。
- 安装根目录不会成为可直接确认的大范围候选。

### Windows 监听与进程

- 捕获临时目录中的增删改名。
- 中文路径可监听。
- 停止后不再接收事件且线程退出。
- 同时只能开始一个会话。
- 监听器准备失败时不启动游戏。
- 启动失败时清理监听器。
- 已配置游戏直接启动时不创建监听会话，发现状态保持 `Idle`，游戏进程仍可正常运行。
- 主 PID 正常退出后进入宽限期并自动分析。
- 主 PID 快速退出时进入手动停止兜底。

### 现有功能回归

- 空来源游戏被自动备份正常跳过。

- 配置完成后可以创建、恢复和自动上传。

## 人工验收重点

### 安全

- 仅选择 EXE但未点击确认时，不新增游戏。
- 已添加待配置游戏不会产生快照或云端对象。
- 开始监测不会启动自动备份，也不会改写真实存档。
- 用户确认目录前，不把任何候选写入 SQLite。
- 移除待配置游戏只删除 SaveLink 记录，不删除 EXE、安装目录或真实存档。

### 生命周期

- 监测中关闭窗口到托盘仍继续工作。
- 游戏正常退出后自动完成分析。
- 启动器场景可以手动停止并分析。
- SaveLink 真正退出后没有遗留监听线程或句柄。
- 重启 SaveLink 后待配置游戏仍存在，但旧临时监测结果不伪装成有效结果。

### 候选质量

- `Hole Is Mine` 的 `GameProgress.hole`、`Achievements.hole`、`Settings.hole` 所在目录进入高可信候选。
- `Player.log`、Unity Analytics、Shader 缓存和 GSE `playtime.txt` 被正确降权。
- Edge、Chrome 等浏览器用户资料目录保持低可信且不可确认，即使其文件在游戏期间发生变化。
- RUNE/CODEX 标准根目录下的 `<纯数字 AppId>` 是游戏级候选；`remote`/`profile_*`/`backup` 变化必须归并到 AppId 容器，不得作为并列推荐项。
- 未知模拟器或一般路径下父子目录同时高可信时，仍全部展示并由用户二选一，不套用 AppId 特殊归并。
- 用户可以看见推荐依据，并能拒绝所有候选后重新监测。

## 不在第一版范围

- ETW 按进程证明文件写入归属。
- 监听整个磁盘。
- Steam 受控 `-applaunch AppID` 已纳入启动绑定；其他商店启动协议和任意命令行参数不在范围内。
- 自动处理所有第三方 launcher、反作弊和管理员权限游戏。
- 多个游戏并行监测。
- 不经用户确认自动绑定候选目录。
- 安装根目录中的精确文件集合保护。
- 将原始监测事件长期写入数据库或上传云端。
