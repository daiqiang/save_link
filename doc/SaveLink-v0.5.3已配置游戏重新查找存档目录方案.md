# SaveLink v0.5.3 已配置游戏重新查找存档目录方案

## 文档状态

- 版本：1.0
- 日期：2026-10-04
- 状态：已实现，待真实游戏验收
- 目标版本：v0.5.3

本文只定义“已配置普通 PC 游戏重新查找存档目录”。它复用现有
`ReadDirectoryChangesW` 动态发现能力，是一轮只读诊断，不属于自动备份或云同步。

## 背景

首次添加未知游戏时，一次游玩不一定会写入全部存档目录。例如游戏可能分别在三个目录
保存进度、配置和角色数据，但第一次动态发现只观察到其中两个。游戏进入正常管理后，用户
仍需要再次游玩并查看文件活动，以发现后来才出现的第三个目录。

与此同时，已经纳入管理的目录也应显示本轮实际修改了哪些文件，帮助用户区分已保护内容
与可能遗漏的内容。

## 产品决定

“重新查找存档目录”同时完成两件事：

1. 汇总每个已管理存档目录在本轮游戏中的文件活动。
2. 展示管理范围之外的其他存档目录候选。

结果只供用户判断。重新查找不会：

- 自动新增、删除或替换游戏的存档目录；
- 提供候选目录复选框或“确认并纳入管理”按钮；
- 创建快照、触发上传、恢复文件或修改游戏文件；
- 改变现有十分钟自动备份机制。

用户确认某个参考候选确实属于存档后，通过现有“编辑游戏”功能手动添加目录。

## 支持范围

v0.5.3 支持同时满足以下条件的游戏：

- 已经配置至少一个存档目录；
- 具有本机普通 EXE 或 Steam 启动绑定；
- 不是 DeSmuME 等模拟器游戏。

待设置目录的普通 PC 游戏继续使用现有“启动游戏并查找存档”流程。没有启动绑定的云端
游戏继续先完成本机绑定。模拟器游戏的启动与文件归属模型不同，本轮不接入。

## 用户流程

1. 用户在已配置游戏详情中点击“重新查找存档目录”。
2. SaveLink 先启动现有广域目录监听，再按已保存的启动绑定启动游戏。
3. 用户正常游玩、保存并退出。
4. 普通 EXE 退出后自动进入五秒宽限期并分析；Steam 或加载器过早退出时，沿用现有
   “停止并分析”兜底。
5. 页面展示只读活动报告。
6. 用户发现遗漏目录时，点击“编辑游戏”并手动添加。

全局同时只允许一个动态发现会话。活动会话存在时，其他游戏不能再启动动态发现。

## 两种发现用途

现有运行时增加用途字段：

```text
initial_discovery  新游戏首次发现
reference_rescan  已配置游戏重新排查
```

两种用途共用监听根目录、进程生命周期、加载器识别、退出宽限、事件合并和候选评分。
重新排查还会检查每个已管理目录：如果它当前存在且不在现有广域监听根之下，就把它
作为额外监听根加入本轮会话；已经被 AppData、文档或安装目录覆盖的路径不重复监听。

差异如下：

| 行为 | 首次发现 | 重新排查 |
| --- | --- | --- |
| 适用状态 | 待设置存档目录 | 已配置 |
| 已管理目录活动区 | 无 | 有 |
| 候选复选框 | 有 | 无 |
| 确认写入目录 | 有 | 无 |
| 首次自动快照 | 确认后按现有规则执行 | 永不执行 |

技术上可以继续复用 `awaiting_confirmation` 阶段名称以控制改动范围，但重新排查界面只显示
“分析完成”，绝不开放确认命令。

## 结果界面

### 已管理的存档目录

每个现有存档目录固定显示一项，不因本轮没有事件而消失：

- `本轮检测到变化`：显示有效事件数、文件数及文件明细；
- `本轮未检测到变化`：仅表示这次游玩没有捕获到变化，不表示目录无效；
- `目录当前不存在`：单独标记，不混入其他候选。

文件明细沿用创建、修改、删除、重命名和补查发现等事件类型。

### 其他可能的存档目录

只显示与所有已管理目录都不重叠的候选，并沿用高、中、低可信度、评分、正向证据和降权
原因。低可信候选继续折叠展示。

本区域不显示复选框。页面提供“编辑游戏”入口，由用户自行决定是否添加。

## 分类规则

分析时先按已管理目录分类事件，再对剩余事件执行现有候选评分：

1. 事件路径等于或位于某个已管理目录之下：归入该目录的活动报告。
2. 候选目录等于或位于已管理目录之下：不再作为新候选重复显示。
3. 候选目录是已管理目录的祖先：不作为新候选，避免诱导用户扩大保护范围。
4. 只有与全部已管理目录无重叠的候选，才进入“其他可能的存档目录”。
5. 多个已管理目录分别聚合，不得把一个目录的事件算到另一个目录。
6. Windows 路径比较忽略大小写，并复用现有规范化规则。

目录事件展开、250 毫秒重复事件合并、单候选文件上限和总事件上限沿用现有实现。

## 数据契约

发现状态增加以下只存在于内存和前端事件中的字段：

```text
mode: initial_discovery | reference_rescan | null
managed_directories: [
  {
    directory,
    exists,
    event_count,
    distinct_file_count,
    last_activity_unix_ms,
    files
  }
]
```

`candidates` 在首次发现中仍表示可确认候选，在重新排查中只表示管理范围外的参考候选。

本功能不新增 SQLite 字段，不迁移数据，不持久化原始文件活动，也不改变云端协议。

## 安全边界

- `confirm_save_discovery_paths` 只接受 `initial_discovery` 会话；后端不能只依赖前端隐藏按钮。
- 重新排查期间编辑或删除当前游戏仍被禁止，避免结果与目录配置错位。
- SaveLink 数据目录、应用数据目录和快照仓库继续排除在监听结果之外。
- 监听结果不保证证明文件由目标 PID 写入，界面必须继续使用“可能”表述。
- 搜索范围沿用现有监听根目录，不承诺覆盖任意磁盘位置；更通用的兜底搜索另行设计。

## 验收用例

1. 已管理 `A`、`B`，本轮修改 `A/slot.sav` 和未知 `C/save.dat`：`A` 显示变化，`B`
   显示未变化，`C` 进入其他候选。
2. 变化仅位于 `A/profile`：只归入 `A`，不把 `A/profile` 重复推荐为新目录。
3. 候选是 `A` 的父目录：不得展示为可补充目录。
4. 本轮没有有效事件：仍列出全部已管理目录并显示未检测到变化。
5. 已管理目录不存在：显示不存在，不让整轮分析失败。
6. 已管理目录位于现有广域监听范围之外：作为额外根监听，并正确展示文件活动。
7. 重新排查结果不出现复选框，不调用确认命令，不修改 SQLite，不创建快照。
8. 首次发现的候选勾选、确认目录和首次自动备份行为保持不变。
9. 普通 EXE 自动结束分析，Steam/加载器继续支持手动停止并分析。
10. 两个游戏不能同时启动发现会话，监测期间不能编辑当前游戏。

## 实施顺序

1. 在平台无关分析层增加已管理目录活动聚合及重叠候选过滤，并补单元测试。
2. 扩展 Tauri 发现会话用途和状态契约，允许已配置普通 PC 游戏启动只读重新排查。
3. 增加已配置游戏入口和双分区只读结果界面，保留原首次发现交互。
4. 运行 Rust、Tauri 与前端构建测试，再做隔离数据的真实窗口冒烟。
